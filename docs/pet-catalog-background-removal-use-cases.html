DB에 과거 backgrounds가 남아 있어도 새 엔티티가 이를 모델링하지 않고, 명시적인 도메인→응답 변환을 거치므로 클라이언트 JSON에는 포함되지 않습니다.

04

02 / USE CASES

실제 동작을 사용자 흐름으로 보기

앱 실행부터 관리자 변경, 레거시 DB 문서 처리까지 다섯 가지 흐름으로 정리했습니다.

UC-01
앱 카탈로그 조회

사용자가 앱을 열어 펫 목록을 본다

클라이언트는 활성 펫만 받고, 서버 배경 URL 대신 각 펫의 colorCode로 화면 배경을 생성합니다.

REQUESTGET /v1/pets/catalog
QUERYisActive=true, 표시 순서 정렬
RESPONSE색상 + 레벨 미디어, 배경 없음
CLIENTcolorCode 기반 배경 렌더링
UC-02
캐시 갱신

클라이언트가 카탈로그 변경을 감지한다

응답 body의 revision을 저장값과 비교합니다. 값이 달라지면 새 카탈로그를 반영하고 URL이 달라진 에셋만 다운로드합니다.

REVISION SOURCE활성 카탈로그 중 최대 updatedAt
RESPONSE항상 200과 전체 body
COMPARE저장한 revision과 비교
CLIENT ACTION변경된 URL의 에셋만 다운로드
UC-03
관리자 CRUD

운영자가 펫을 생성하거나 수정한다

관리자 POST/PUT 요청에서도 배경 객체를 받지 않습니다. 색상은 #RRGGBB 형식으로 검증하고, 레벨별 이미지·Lottie URL은 계속 관리합니다.

CREATEPOST /v1/admin/pet-catalog
UPDATEPUT /v1/admin/pet-catalog/{type}
ACTIVATEfalse → true만 허용
OUTPUT모든 관리자 응답에도 배경 없음
UC-04
레거시 DB

기존 문서에 backgrounds가 남아 있다

신버전 코드가 먼저 배포되면 과거 MongoDB 필드는 응답으로 새어 나오지 않습니다. 다만 “DB에서도 제거”라는 완료 조건을 만족하려면 안전장치가 있는 수동 migration을 실행해야 합니다.

READ미매핑 과거 필드는 응답 DTO에 전달되지 않음
MIGRATION$unset backgrounds
VERSIONupdatedAt을 같은 시각으로 갱신
VERIFY잔여 0건, 전체 문서 수 불변
UC-05
초기 시딩

비어 있는 DB로 서버가 처음 시작한다

컬렉션이 비어 있을 때만 기본 5종을 생성합니다. 신규 문서에는 처음부터 backgrounds가 없으며, DB에 데이터가 하나라도 있으면 시더는 기존 구성을 건드리지 않습니다.

CHECKrepository.count() > 0이면 종료
EMPTY DB기본 5종 insert
FIELDS색상·순서·levels 저장
NO UPDATE기존 문서의 updatedAt 수정 없음
